# 文风复刻与内容事实的边界

这个 Skill 参考作者**怎样用词、组织句子、安排和讲述材料**。写得像作者不意味着替作者编造经历、态度或观点；文风参照也不能充当新主题的事实来源。`scenarios/` 里提供了可直接阅读的原文节选，无全文库，也没有需要读取的其他文章文件。

## 哪些可以借鉴

| 内容 | 正确处理方式 |
|---|---|
| 语气、措辞、句式、进入话题的方式、段落推进和解释深度 | 从用户样文或内置片段观察，再按当前题材与用途调整 |
| 历史案例中的库、命令、参数、版本、路径与工程结构 | 只用于理解当时的叙述，**不能当作新项目事实复制** |
| 历史案例里的截图、效果、测试结论、第一人称经历 | 不视为当前任务证据；不可将“我测过”“我踩坑了”移植到新稿 |
| 当前任务中的代码、功能、环境、兼容性、真实效果 | 依靠用户提供的文件、日志、当前项目和可靠核验 |
| 非技术文章中的事件、引语、数据、个人感受和立场 | 依靠当前素材或可靠来源；样文中的旧经历与旧观点不自动代表本次想法 |

## 具体写作判断

1. **用户给出源码、日志或现有草稿：** 保留其中可确定的事实、接口、路径和限制，不随意改写技术意义；未展示的测试结果不要补写。
2. **用户只有主题：** 可围绕主题组织草稿，个人经历和立场留在用户已表达的范围内。事实性内容按需要核验；技术主题遇到变化快的接口、版本、配置时先查对应资料，未核实的关键步骤不能写成“已验证可用”。
3. **参考案例有完整操作过程，但本次材料没有：** 借鉴“什么时候给示例、什么时候解释”的思路，不凭案例内容给新任务编造操作步骤。
4. **参考案例出现“我发现”“我试了”：** 可以学习第一人称口气，但事实依据必须来自本次任务。Agent 在当前环境的验证只能写成当前验证，不能冒充用户过去的亲历；非技术稿同样不凭空编造旅行、对话、情绪或个人回忆。
5. **参考案例出现图片和外部链接：** 它们只是原文结构的一部分，**并非 Skill 提供的可用资产**。新稿只引用当前实际存在的图片与链接。
6. **关键信息缺失：** 尽量完成有材料支持的部分；需要验证的环节明确其状态，必要时留待补项。

## 两种通用的迁移方式

- 看到场景节选「先给项目结构，再给最小代码，之后逐项解释」，可以学习**把前置材料放到读者刚好需要的位置**；新稿的项目结构、代码和运行结果必须来自新任务。
- 看到场景节选「明确列出已测试与未测试范围」，可以学习**说明证据边界**；如果新任务没有测试数据，就不要虚构环境或“全部兼容”的结论。

**核心区分：** 历史文字提供写法证据，当前材料提供事实证据。二者不能互相代替。
