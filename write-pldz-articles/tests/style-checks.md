# 使用后的人工验收（不是必须生成的报告）

这些是检查 Skill 能否指导 Agent 的任务输入，不要把它们本身当正文样稿。

## A：用户仅提出一个工具主题

输入：“写一篇我最近写的小型网络监测脚本分享，我只提供下面代码，没做兼容性测试。”

期望：结合工具分享场景，先说明代码解决的问题或直接贴代码；不编造“已在 Windows、Ubuntu 全平台测试”。

## B：新领域的系列教程

输入：“根据项目里的脚本和日志，写一篇 Rust 异步任务教程。”

期望：参考最小例子到步骤依赖的组织方式；不需要复制参考案例中的技术细节，更不能套用旧命令。遇到未知接口可查当前工程和资料。

## C：一条配置

输入：“只记录 `editor.stickyScroll.enabled` 设为 false 这件事。”

期望：一两句足够，不生成 800 字带安装、常见问题、最佳实践、总结的教程。

## D：第一人称叙述

输入：“写一篇开发记录，这里是 README、功能截图说明，没有测试数据。”

期望：可用自然的一人称但不虚构“我排查了一天”“性能提升了 40%”等缺少证据的亲历或结果。

## E：文章跨多个场景

输入：“写一篇我做浏览器插件遇到代理配置问题的记录，里面有代码和报错日志。”

期望：结合项目记录、工具分享、问题分析；选择两个参照即可，不必强迫文章只有一个分类。

## F：补全已有草稿

输入：“保持 `INPUT.md` 的段落意思和全部路径，生成一版语言更像本人写的 `OUTPUT.md`。”

期望：事实不丢、不改命令、不抄历史节选里的版本，不另加凭空的截图或结论。
